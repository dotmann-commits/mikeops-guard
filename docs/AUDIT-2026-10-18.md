# MikeOps Guard: security, correctness and performance audit

Date: 18 October 2026.
Version audited: 0.1.0 at commit `dc07a93`.
Method:
- Read all of `src/` (about 3,200 lines), the tests, the README, CI and `action.yml`.
- Ran the test suite.
- Measured real scans of three repositories with all six scanners installed (macOS, Intel, Node 22).

Nothing in this audit claims runtime security. Guard is static analysis: it finds known patterns in files and history. It can miss issues, and every finding should be confirmed by a person.

## Baseline (before changes)

| Measure | Result |
|---|---|
| Tests | 80 passed (81 after the symlink fix), suite takes 10.7 s |
| Sample repo (`test/fixtures/sample-repo`) | 2.1 to 2.6 s, 17 findings |
| Guard's own repo | 2.6 to 2.8 s, 0 findings |
| MikeOps-Acquisition (17k files, 14.5k in `node_modules`) | 8.0 to 15.3 s, 41 findings |
| Slowest scanner in every run | `trivy-config`: 2 to 15 s. Others run in parallel and finish in about 6 s or less |

## Findings, highest priority first

### P0: correctness and safety

**A1. An incomplete scan can read as clean.**
- *Evidence:* `run.ts` sets `passed` from findings only. `console.ts` and `html.ts` print "PASSED" even when a scanner failed or was skipped because it is not installed. Scanners disabled in the config are filtered out before the run, so they appear nowhere in the report.
- *Risk:* a JSON consumer or a person reading "PASSED" believes code was checked that was not. The policy file comes from the scanned repository, so in CI a pull request could disable scanners without the report showing it.
- *Change:*
  - Add a report-level `status` (`passed`, `failed`, `incomplete`) and `coverage` (scanners that ran, and those that did not, with reasons).
  - Disabled and unselected scanners appear as outcomes.
  - Console and HTML show INCOMPLETE.
  - `passed` and exit codes keep their meaning.
- *Acceptance:* tests show a failed, unavailable or disabled scanner gives `status: incomplete` and an INCOMPLETE verdict, while a not-applicable skip (for example no Dockerfiles) does not.

**A2. Terminal escape injection.**
- *Evidence:* `console.ts` prints titles, messages, file paths, reasons and AI explanations unmodified. Those strings come from scanners reading the target repository, or from a language model.
- *Risk:* a crafted file name or workflow could clear the screen, hide findings, fake a PASSED line or inject terminal hyperlinks.
- *Change:* strip control characters (C0 except tab and newline, DEL, and C1, which includes ESC sequences) from every untrusted string before it reaches the terminal.
- *Acceptance:* a test with an ESC sequence and a carriage return in a title and a file name shows neither in the output.

**A3. The scanned repository can send finding data off the machine.**
- *Evidence:* `explain.enabled` and `explain.host` are accepted from the repository's `.mikeops-guard.yml`.
- *Risk:* a repository can turn explanations on and point them at any host, so a plain `mikeops-guard scan` posts rule names, file paths and messages to a server the repository chose.
- *Change:* a config file found inside the target may only use a loopback Ollama host. A remote host needs a config passed with `--config` from outside the target. Otherwise the scan prints why and uses the default local host.
- *Acceptance:* tests cover a repository config with a remote host (refused, with a warning), a loopback host (allowed), and an outside `--config` (allowed).

**A4. Binary lookup trusts relative PATH entries.**
- *Evidence:* `resolveBinary` joins every PATH entry, including `.` or `bin`, which resolve against the current directory.
- *Risk:* when run inside the target repository with such a PATH, a committed executable named `trivy` or `gitleaks` would be run.
- *Change:* ignore PATH entries that are not absolute.
- *Acceptance:* a unit test shows a relative entry is never used.

**A5. No general secret redaction.**
- *Evidence:* Gitleaks values never reach a report. But messages from other scanners, scanner error text (stderr tails) and AI explanations are written to the console, JSON and HTML, and are sent to Ollama, unmodified.
- *Risk:* a token quoted in a workflow message, a tool error or an explanation would be saved in a report artifact.
- *Change:* redact well-known token formats (GitHub, AWS access key ID, Slack, Stripe live keys, Google API keys, private key blocks, JWT-shaped values, generic `password=`, `secret=`, `token=` assignments) in every finding text field, scanner reason and explanation, and before anything is sent to Ollama.
- *Acceptance:* tests plant each format in a message, a reason and an explanation, and assert none appears in console, JSON, HTML or the Ollama prompt.

### P1: reliability, reproducibility and performance

**B1. Fingerprints change when unrelated lines move.**
- *Evidence:* `fingerprint.ts` hashes scanner, rule, file, **line** and message.
- *Risk:* an ignore rule keyed by fingerprint stops matching after an edit above the finding. Two identical findings in one file share a fingerprint.
- *Change:* fingerprint version 2 uses scanner, rule, file and normalised message, plus an occurrence index within the file. Ignore rules still accept version 1 fingerprints.
- *Acceptance:* tests show a line shift keeps the fingerprint, duplicates get distinct fingerprints, and a version 1 ignore still matches.

**B2. HTML Content Security Policy allows any inline script.**
- *Evidence:* `script-src 'unsafe-inline'`. Values are escaped, so this is defence in depth.
- *Change:* allow only the report's own script, by its SHA-256 hash.
- *Acceptance:* a test checks the CSP contains the hash of the embedded script and no `unsafe-inline` for scripts.

**B3. Trivy config walks `node_modules` and `.git`.**
- *Evidence:* Guard's discovery always skips them, but Trivy is only given user excludes.
- *Measured:* Trivy took 3.2 to 5.2 s on MikeOps-Acquisition and 4 to 7 s on a pnpm monorepo web app (22,784 of 23,157 files in `node_modules`). Skipping both took 2.5 s and 3 s, with **identical findings** in both repositories.
- *Change:* pass `--skip-dirs` for `**/node_modules` and `**/.git` to `trivy config` only. Dependency scanning is unchanged, because installed packages can matter there.
- *Acceptance:* a test checks the arguments, and the measured scan time drops with the same findings.

**B4. CI never builds and tests one Node version.**
- *Evidence:* `ci.yml` runs typecheck, lint and tests on Node 22 only. `engines` says Node 20 or newer, and `npm run build` never runs in CI.
- *Change:* a Node 20 and 22 matrix, and a build step.
- *Acceptance:* actionlint and Guard's own workflow audit pass on the new workflow.

**B5. Timeouts kill only the direct child process.**
- *Evidence:* `exec.ts` sends SIGKILL to the scanner, not its process group. For example, Gitleaks runs `git`.
- *Status:* documented as a remaining risk. Killing process groups needs detached children plus clean-up on Ctrl+C, which is a larger change.

**B6. The policy file in the scanned repository controls CI strictness.**
- *Status:*
  - A1 makes disabled scanners visible.
  - The README should recommend that CI passes a trusted config (`config:` input) for pull requests from forks.
  - Enforcing that is a product decision.

### P2: high-value checks for AI-generated applications

AI-generated web apps (Vite, Next.js, Expo, with Supabase) repeat a few mistakes that existing scanners do not target:

| # | Check | Why it matters |
|---|---|---|
| C1 | A server secret in a public frontend variable (`VITE_`, `NEXT_PUBLIC_`, `EXPO_PUBLIC_`, `REACT_APP_` with `SERVICE_ROLE`, `SECRET` or `PRIVATE` in the name) | These prefixes are compiled into the browser bundle, so the value is public |
| C2 | The Supabase service role key referenced in frontend source | It bypasses all Row Level Security |
| C3 | A Supabase migration creates a table without enabling Row Level Security | The table is readable and writable with the public anon key |
| C4 | A Supabase policy allows writes `using (true)` or `with check (true)` | Any user, or anyone with the anon key, can change every row |
| C5 | A public Supabase storage bucket | Files are readable by anyone with the URL |
| C6 | A committed `.env` file (not `.env.example`) | Secrets in version control |

These are pattern checks on files. They can be wrong both ways, for example RLS enabled in a later migration. The benchmark below measures that on fixtures.

### Performance, before and after (same machine, same repositories, warm caches)

| Target | Before | After |
|---|---|---|
| Sample repo, 6 scanners (7 after) | 2.1 to 2.6 s | 1.6 s (3 runs) |
| Guard's own repo | 2.6 to 2.8 s | 1.8 s (3 runs) |
| MikeOps-Acquisition (17k files) | 8.0 to 15.3 s | 4.5 to 4.9 s (3 runs) |
| Test suite | 10.7 s, 80 tests | 7.0 s, 110 tests |

**Where the gain comes from:** the slowest scanner, `trivy config`, no longer walks `node_modules`. On a pnpm monorepo where 22,784 of 23,157 files are in `node_modules`, Trivy took 4 to 7 s before and 3 s after, with identical findings. The new `app-security` scanner adds 7 to 47 ms per repository. The sample-repo gain is mostly run-to-run variance in Trivy's start-up, so the large-repository numbers are the meaningful ones.

### Detection benchmark (`test/unit/app-security-benchmark.test.ts`)

**Labelled fixtures:**
- 11 of 11 planted issues found at the right line (recall 100%).
- 0 findings in the safe set (precision 100% on the traps).
- The traps:
  - server-only service role use, including a TanStack Start server route outside any `api` folder;
  - public read policies and `service_role`-only policies;
  - commented-out SQL and SQL inside function bodies;
  - a non-public schema and a SQLite migration;
  - a Node CLI that mentions the key name;
  - build output.

**Real repositories (read-only, 8 private projects):**

| Round | Result |
|---|---|
| First run | 36 findings. Hand review found 4 false positives: two TanStack Start server routes, Guard's own rule source, and SQLite migrations treated as Supabase. Public-form insert policies were rated high, which overstated them |
| After fixing those classes (each now a safe fixture) | 0 false positives. All 22 high or critical findings were confirmed real against the migrations. 12 low findings are insert-only public forms, rated low on purpose |

Confirmed issues included:
- policies named for the service role but missing `TO service_role`, so `FOR ALL USING (true)` applied to the public anon key (a travel platform);
- 16 tables without RLS, two of which had policies that therefore did nothing (a retail operations app).

These are reported to the project owner separately and are not named here.

**Limits:** pattern checks see files, not the live database. RLS enabled in the Supabase dashboard rather than in migrations is not visible, and messages say to verify.

### Remaining risks

- **On Windows, timeouts and cancel stop only the scanner process.** Windows has no process groups. macOS and Linux are covered since 21 October.
- **The repository's policy file still controls strictness in CI (B6).** It can set `failOn: none` or ignore rules. That is now visible (disabled scanners, the INCOMPLETE status, the config path in the output). For pull requests from forks, CI should pass a trusted `config:`.
- **Redaction is pattern based.** Unknown credential formats can pass through scanner messages. Gitleaks remains the primary secret control.
- **The app checks are static.** They do not prove a deployed app is safe or unsafe.

### Recommended next steps

3. C6 committed `.env` detection with `git ls-files`.
4. ~~Process-group timeouts (B5).~~ Done 21 October.

6. A published release (npm and a prebuilt bundle) so installs are reproducible without building.

## Follow-up, 21 October 2026

Two more gaps found when reviewing the 18 October work, plus B5. Each was a separate commit with tests.

| Item | Change | Evidence |
|---|---|---|
| D1 unbounded reads | Built-in scanners read files from the scanned repository with no size limit (`workflow-audit`, `package.json` in `app-security`), and `app-security` opened every source file at once. Now `core/files.ts` reads at most a limit from an open handle, and `mapLimit` keeps 32 reads in flight | `files.test.ts`, `concurrency.test.ts` (peak concurrency equals the limit) |
| D2 silent partial checks | An oversized file was skipped without a trace. Now it is listed in the scanner outcome. Workflows, SQL, env files and Supabase configs mark the scanner `incomplete`. Oversized JavaScript is listed only | `oversized-files.test.ts` |
| B5 process groups and Ctrl+C | Scanners run in their own process group, and timeouts kill the group. SIGINT and SIGTERM stop every scanner, remove temp files, write no report and exit 130. A second signal exits at once | `exec.test.ts` (a helper process started by the scanner is gone after timeout and cancel), `cancel.test.ts`, and `interrupt.test.ts`, which sends a real SIGINT to the built CLI |

**Reproduction of B5 before the fix:** with the 0.1.0 kill (`child.kill('SIGKILL')`), a helper started by the scanner was still running after the timeout. With the new code it is gone.

**No regression:**
- Findings are identical to the 18 October code on the sample repo (17) and MikeOps-Acquisition (48), with the same rules, files and lines.
- Scan times are within run-to-run noise: 2.2 to 2.8 s and 4.5 to 5.1 s for both versions, run alternately.
- Tests: 126 of 126 pass, three runs in a row.
- `engines` is now Node 20.3 or newer, for `AbortSignal.any`.
- CI builds before testing, so the real Ctrl+C test runs there.
